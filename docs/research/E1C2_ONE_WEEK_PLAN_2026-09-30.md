## 1. 交付承诺与研究目标

一周按约32–40小时有效开发时间安排，依赖网络、镜像和执行器可用。可以计划完成工程实现、边界测试、DEV消融、冻结协议、独立验证记录及交接；不能预先保证随机模型和未知任务30/30成功。

用户要求的严格目标继续保留：单一冻结方法、无人工选文件、无公开断言输入、旧DEV30一次完整30/30 official resolved，再选择全新Fresh30。未达到就如实停在门槛前，不能换分母、换评价口径或汇总跨版本best-of制造“完美”。工程测试零失败是交付条件；实验负结果也是有效交付，不能改测试掩盖。

## 2. 主假设和实现范围

**候选方法：固定行为合同的反馈受限复现。** 从允许的issue自然语言抽取行为合同，再生成最小probe；执行反馈允许修正调用构造、导入和已声明环境条件，但不允许为了变绿而改写预期行为。先在旧DEV实现，不修改当前canary v2。

合同建议字段：`issue_quote_span`、`observable_kind`、`preconditions`、`action`、`expected_relation`、`source_evidence_ids`、`confidence/abstain_reason`。仅支持异常、API调用完成、明确值/类型关系三类已有可观测要求；无法从公开需求确定时弃答。跨度须对应允许投影，不能引用被剥离的测试代码。

执行顺序：允许输入 → 自动定位 → 合同 → probe → 两次base执行 → 候选锁定 → 独立Gold判别/语义审计。生成侧不得看到Gold内容、官方失败断言或评分结果；独立评分只在候选锁定后进行，不再反馈同一独立样本的生成。

新的DEV版本最多两轮显式候选修订，记作不同候选并计入同一任务预算。传输/限流/扣费失败不自动重试。分类为setup错误时，只能使用公开环境证据修正setup；不得将“删掉检查”当修正。任务ID只供控制器记账，不进入定位或probe生成特例表。

复用现有源码窗口、SafeWorkspace、预算账本、静态检查与隔离容器；本周不增加图框架、训练大模型或重新造评测平台。重点新增合同保真检查和失败归因，避免继续堆版本。

## 3. 为什么值得做，以及尚未证明什么

现有DEV v4有5个重复失败候选、4个Gold可区分；人工审核仍是可信度结论的一部分。先前v3暴露额外强断言，说明仅提高“运行失败率”可能偏离issue。要检验的是合同约束能否降低无依据断言，并在相同预算下保持或增加可信覆盖。

相关研究核验于2026-09-30；这里只做有限范围的一手来源核验，不声称完成全面新颖性检索：

| 一手来源 | 已有思想 | 本计划如何使用 / 区别 |
|---|---|---|
| [SWT-Bench](https://arxiv.org/abs/2406.12952) | 将issue转成base失败、修复后通过的测试 | 采用复现与修复分开的指标，不能把该任务本身称原创 |
| [Agentless](https://arxiv.org/abs/2407.01489) | 定位、修复、验证的简洁分阶段流程 | 复用简洁流程，重点验证更严格的输入来源约束 |
| [Echo](https://arxiv.org/abs/2603.07326) | 代码图检索、执行反馈、候选补丁辅助复现验证 | 图检索+反馈已有先例；本计划用独立grader并限制行为合同漂移 |
| [ReProAgent](https://arxiv.org/abs/2607.09123) | 定位、根因、测试规划、测试生成分阶段 | 多阶段也不是新颖点；比较合同约束是否有额外价值 |
| [SWE-Tester](https://arxiv.org/abs/2601.13713) | 训练开源模型生成issue复现测试 | 本周采用固定Flash，不投入训练数据与GPU |
| [Multi-SWT-Bench](https://arxiv.org/abs/2609.34752) | 跨语言复现评测，指出setup及行为保持困难 | 仅借鉴失败分类，不扩语言/样本范围 |

潜在贡献是严格输入隔离下的合同保真机制、可审计弃答与受控成本消融。它与现有工作部分重叠；只有同预算比较和独立canary支持后，才可写“取得增益”。本周不宣称SOTA、全新算法或无污染模型：公开基准可能已在模型训练数据中。

## 6. 实验和预算

DEV消融只用现有DEV12（9条双准入，另外3条固定分母保留）。A为v4风格生成，B为固定合同+受限反馈；同模型、相同输入源码预算、相同候选数与单题provider上限。旧v4结果只是历史参照，不冒充本次匹配A臂。主分析为B与A的可信任务差、无依据断言数、弃答原因和总tokens；小样本以逐题配对和描述性结果为主，不夸大显著性。

建议保守预算：

- DEV-A：最多18请求，总≤90,000 tokens；DEV-B：同样上限。每题两请求共享10,000 tokens，预检放不下即原位停止，不借用其他任务预算。
- 独立canary：最多3请求、42,000 tokens；沿用既有v2时严格使用原协议，不增加候选。
- 通过后的3题两臂修复：最多6请求、60,000 tokens；另立协议，不将这一建议当作现成runner。
- 一周建议累计停止线282,000 provider tokens（含上述全部阶段），不是消费目标。任何单实验仍≤100,000；DEV无增益就跳过后续付费阶段。记录缓存命中、失败扣费和实际模型返回名。
- 同版DEV30和Fresh30不包含在以上预算；若门槛达成，先给出可执行命令与分批但同身份的预算账本，再开始。不开无上限连续实验。

这里的DEV-A/B与修复命令尚未实现/冻结，不能虚构CLI。WebCodex完成实现和零调用preflight后，须输出实际精确命令和摘要；已有≤100,000 tokens实验授权不免除身份、预算和数据边界核验。

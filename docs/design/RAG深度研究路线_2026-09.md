# AI Coding Agent：深度 RAG 研究路线（Research Roadmap）

> 基于当前 `agent-service-toolkit` 改造项目与 `PROGRESS(2).md` 整理。  
> 更新时间：2026-09-17  
> 目标：**停止横向堆 Agent 功能，把现有 Coding Agent 作为实验底座，深入做一个“有明确研究问题、有算法、有数据集、有消融、有结论”的新型 RAG。**

---

# 0. 先定一个总方向

## 暂定研究题目

### Evidence-Guided Adaptive Code RAG
### 基于证据状态与效用决策的自适应代码 RAG

中文可以叫：

> **证据引导的自适应代码检索**
>
> 或
>
> **面向 Coding Agent 的证据门控自适应 RAG**

注意：

**现在不要直接宣称“提出了一种全新的 RAG 算法”。**

目前应该叫：

> **研究方案 / working hypothesis**

只有经过真实任务集 + 消融实验之后，才能决定它是不是足够形成“新方法”。

---

# 1. 为什么现在应该做 RAG，而不是继续加功能

当前项目已经不是“功能太少”的问题。

已有：

- Coding Agent
- `search_code`
- Planning
- CodeGraph
- Test / Debug / Self-Correction
- Reviewer
- HITL
- Sandbox
- Trajectory
- Experience Memory
- Experience Retrieval
- EGCP Evidence Gate
- A/B Harness
- SWE 风格独立判分
- Cost Tracking

这些能力已经足够构成一个完整实验底座。

所以从现在开始：

> **继续加 10 个工具 ≠ 研究深度增加。**
>
> **真正新增研究价值的，是证明“什么代码应该被取、为什么取、什么时候停止取”。**

当前日志也已经出现了一个非常重要的实验信号：

- 仅文件读取：约 94k token
- `search_code`：约 121k token
- CodeGraph：约 384k token
- CodeGraph + Evidence Gate 修复后：约 135k token

这些数据样本极小，不能证明谁更好，但暴露了一个很值得研究的问题：

> **更多代码证据并不会自动带来更好的 Agent。**
>
> Retrieval 能力越强，可能同时把成本和无效上下文一起放大。

因此真正值得研究的是：

> **如何在“检索充分”和“检索过量”之间做动态决策。**

# 3. 真正的研究问题

不要把研究问题写成：

> “怎么让 RAG 检索更准？”

这个太普通。

建议把问题提升成：

> ## Coding Agent 在解决代码任务时，如何判断“当前证据已经够用”，以及“下一次检索是否值得”？

进一步拆成两个问题：

### Q1：Evidence Sufficiency

> 当前收集到的代码证据，是否已经足以支持当前计划步骤？

形式化：

```text
sufficient(E_t, task, plan) -> {True, False}
```

这里的 `E_t` 是当前已经拿到的证据状态。

---

### Q2：Retrieval Utility

即使证据还不完整：

> 再检索一次到底值不值得？

形式化：

```text
worth_more(E_t, action, budget) -> {True, False}
```

考虑：

- 预计增加多少证据覆盖
- 预计增加多少 token
- 是否已有重复信息
- 是否进入 diminishing returns
- 当前任务是否已经足够支持下一步

---

# 4. 核心假设

整个研究可以先压缩成一个非常简单的 hypothesis：

> **H1：代码 Agent 的检索质量不仅由“检索到什么”决定，还由“什么时候停止检索”决定。**

进一步提出：

> **H2：在相同 token/context budget 下，根据 Evidence State 动态选择检索动作，比固定 Top-K / 固定工具链更有效。**

再进一步：

> **H3：把 lexical、semantic、structural、episodic retrieval 放到同一个 evidence state 中进行动态选择，可以减少无效代码上下文。**

最终目标不是：

> “检索越多越好”

而是：

> **“用最少的代码证据，跨过任务所需的充分性阈值。”**

# 5. 你的“新 RAG”应该长什么样

## 5.1 基础版

```text
User Task
   ↓
Task Understanding
   ↓
Query / Intent
   ↓
Retriever
   ↓
Top-K Context
   ↓
LLM
```

这是普通 RAG。

---

## 5.2 你的目标版

```text
                 ┌────────────────────┐
                 │      User Task     │
                 └─────────┬──────────┘
                           ↓
                  Task / Intent Parser
                           ↓
                 Evidence Requirement
                           ↓
        ┌──────────────────┼──────────────────┐
        ↓                  ↓                  ↓
   Lexical Search     Semantic Search    CodeGraph Search
(search_code/BM25)      (BGE-M3)       (symbol/call/test)
        ↓                  ↓                  ↓
        └──────────────────┼──────────────────┘
                           ↓
                  Candidate Fusion
                           ↓
                  Evidence State
                 ┌─────────┼─────────┐
                 ↓         ↓         ↓
              Target     Impact   Verification
                 └─────────┼─────────┘
                           ↓
                  Evidence Coverage
                           ↓
              ┌────────────┴────────────┐
              ↓                         ↓
        Evidence Enough?           Not Enough?
              ↓                         ↓
            STOP                 Worth More?
                                        ↓
                          ┌─────────────┼─────────────┐
                          ↓             ↓             ↓
                      lexical       graph/test    experience
                          └─────────────┼─────────────┘
                                        ↓
                                  Update Evidence
                                        ↓
                                  Repeat / Stop
```

这里真正值得研究的不是某一个 embedding。

而是：

> **把 Retrieval 从“一次 Top-K”变成“Evidence Acquisition Policy”。**

---

# 6. 真正的算法核心：Evidence State

建议把整个 RAG 的状态抽象成：

```python
EvidenceState(
    target_coverage,
    impact_coverage,
    verification_coverage,
    redundancy,
    uncertainty,
    token_cost,
    retrieval_round,
)
```

---

## 6.1 Target Coverage

回答：

> 我到底有没有找到真正要修改的位置？

例如：

```text
目标文件是否存在
目标 symbol 是否存在
symbol 的定义是否定位
相关行是否读取
```

---

## 6.2 Impact Coverage

回答：

> 我知道这个修改会影响谁吗？

例如：

```text
callers
callees
imports
相关接口
依赖模块
```

---

## 6.3 Verification Coverage

回答：

> 我知道修改后应该怎么验证吗？

例如：

```text
相关测试是否存在
测试文件是否读取
FAIL_TO_PASS 是否明确
接口调用链是否明确
```

---

## 6.4 Redundancy

一个非常值得加入的变量：

> 当前拿到的上下文，有多少是在重复表达已经知道的信息？

例如：

```text
file A  1200 tokens
file B   900 tokens
file C  1000 tokens

其中 70% 内容只是重复调用链 / import / 相同定义
```

那么继续 Top-K 很可能是在浪费 context。

---

## 6.5 Uncertainty

增加一个：

```text
uncertainty
```

用于表达：

> 当前模型虽然“找到了一些东西”，但关键关系仍然不确定。

例如：

```text
目标 symbol 找到了
↓
但有 4 个 callers
↓
没有确定哪一个与 issue 相关
↓
uncertainty 高
```

这时候应该继续取证，而不是因为 Top-K 已经满了就停止。

```text
A5 = callee_search
A6 = impact_analysis
A7 = related_test_search

```

# 8. 给每一个 Retrieval Action 定义“证据收益”

每个动作都不是简单的：

```text
score = similarity
```

而是：

```text
Utility(action)
=
ExpectedEvidenceGain(action)
/
ExpectedCost(action)
```

可以进一步变成：

```text
U(a | E)
=
ΔCoverage(a)
+ λ1 * ΔUncertainty(a)
- λ2 * Redundancy(a)
- λ3 * Cost(a)
```

其中：

- `ΔCoverage`：预计能补多少证据缺口
- `ΔUncertainty`：预计能减少多少不确定性
- `Redundancy`：和已有上下文重复多少
- `Cost`：token / latency / tool-call 成本

---

# 9. 这就是你真正可能形成“新意”的地方

不是：

> “我用了 BGE-M3。”

也不是：

> “我用了 CodeGraph。”

因为这些本身都不是你的核心创新。

你的研究对象应该是：

> ## Retrieval as Evidence Acquisition

也就是：

> **把 Coding Agent 的代码检索看成一个“逐步获取证据”的决策问题，而不是一次性相关性排序问题。**

---

# 10. 与普通 RAG 的本质区别

| 普通 RAG | 你的目标 RAG |
|---|---|
| query → Top-K | task → evidence state |
| 主要看相似度 | 看证据缺口 |
| 固定 K | 动态停止 |
| 只考虑 relevance | relevance + coverage + uncertainty |
| 检索工具固定 | 动态选择 retrieval action |
| 很少考虑成本 | token/call/latency 成本显式进入决策 |
| 找到就塞给 LLM | 先判断是否重复、是否足够 |
| 很少 abstain | 可以明确 `abstain` |
| 检索与 Agent 分离 | Retrieval 本身就是 Agent decision loop |

# 11. 你的系统可以形成一个“RAG Policy”

最重要的新增模块可以先叫：

```text
adaptive_retriever.py
```

它的职责不是自己搜索。

而是：

> **决定下一步该调用哪个检索器。**

伪代码：

```python
def retrieve_until_sufficient(state):

    while True:

        if sufficient(state):
            return STOP

        candidates = available_actions(state)

        action = select_action(
            candidates,
            evidence_state=state.evidence,
            budget=state.budget
        )

        if action is None:
            return ABSTAIN

        result = execute_retrieval(action)

        state = update_evidence(
            state,
            result
        )
```

# 12. 第一版算法不要做复杂

第一版不要一开始训练模型。

先做：

## Rule-based Adaptive Retrieval

例如：

```text
if target < 0.8:
    lexical / symbol_search

elif impact < 0.6:
    callers / callees / impact_analysis

elif verification < 0.6:
    related_test_search

elif uncertainty > threshold:
    semantic / experience retrieval

else:
    STOP
```

这样第一版非常容易解释。

# 13. 第二版再做真正的 Adaptive Policy

当第一版实验跑出来以后：

```text
State
 ↓
available actions
 ↓
utility estimation
 ↓
best action
```

再进一步：

```text
policy(state) -> retrieval_action
```

例如：

```text
Task Type = bug
Target = high
Impact = low
Verification = medium
Redundancy = high

→ 不再继续 semantic search
→ 直接 caller search
```

这时候就从“规则 RAG”开始变成：

> **Evidence-aware retrieval policy**

建议你自己定义：

# 26. 你的一个很有意思的研究点：Negative Retrieval

不要只记录：

```text
找到什么
```

还要记录：

```text
哪些检索结果其实应该被拒绝
```

例如：

```text
semantic similarity = 0.82
但是：
- 不同语言
- 不同模块
- caller 不匹配
- repo version 不一致

→ relevance = false
```

这和你现在已经实现的：

```text
experience compatibility
abstain
stale experience
```

非常容易接起来。

# 27. 可以进一步做“Contradictory Evidence”

这是后期非常值得研究的方向。

例如：

```text
Evidence A:
symbol X 在 file A

Evidence B:
另一个同名 symbol X 在 file B

Evidence C:
test 只调用 file B

```

这时候不是：

```text
Top-K > stop
```

而应该：

```text
conflict = true
↓
继续 retrieval
↓
确认真实 target
```

于是你的 RAG 进入：

> **Evidence Conflict Resolution**

这个比单纯“增加 top-k”更有研究味道。

```text
 |    +-- symbol
 |         |
```

这是后期可以继续深入的第二条研究路线。

# 32. 第一版 `retrieval_policy.py`

不要 LLM。

先做确定性算法：

```python
def choose_next_action(state, actions):

    candidates = [
        a for a in actions
        if a.can_run(state)
    ]

    scored = [
        (
            a.estimate_gain(state)
            / max(a.estimate_cost(state), 1e-6),
            a
        )
        for a in candidates
    ]

    return max(scored, key=lambda x: x[0])[1]
```

这样你非常容易解释：

> 我不是让 LLM 随便决定下一步搜什么，而是用 Evidence Gain / Cost 计算下一步检索动作。

# 36. 最终研究故事可以变成

> 现有 Coding RAG 通常把代码检索当作一次性 relevance ranking 问题。
>
> 但 Coding Agent 的真实需求是一个连续的信息获取过程：Agent 在解决任务过程中不断发现新的不确定性，因此不同阶段需要不同类型的代码证据。
>
> 本项目将代码 RAG 建模为 Evidence Acquisition Process：
>
> 1. 建立 Evidence State；
> 2. 识别当前证据缺口；
> 3. 从 lexical / semantic / structural / episodic retrieval 中动态选择下一步动作；
> 4. 根据 evidence gain、uncertainty reduction、redundancy 与 cost 计算 retrieval utility；
> 5. 达到证据充分性后停止；
> 6. 在固定 context budget 下进行 evidence-aware context packing。
>
> 最终目标不是让 Agent 阅读更多代码，而是让它以更低的检索成本获得足够支撑代码修改的证据。

# 45. 可以参考的近期研究趋势

2026 年已经出现了直接针对 Coding Agent context retrieval 的 benchmark：

- **ContextBench**：强调 coding agent 中间过程的 context retrieval，包含 1,136 个 issue-resolution tasks、66 个 repositories，并衡量 context recall / precision / efficiency。
- **Agent Retrieval Bench**：把 repository retrieval 作为 Coding Agent 的上游问题，包含 427 个样本、25 个 repositories，并专门研究 selective retrieval、no-gold / counterfactual controls 与 budgeted context yield。
- **CORE-Bench**：进一步把 agentic coding 下的 code retrieval 分成 code understanding、issue-to-edit localization、broader context retrieval，并指出传统代码检索能力与 agentic coding retrieval 之间存在明显差距。

这些工作说明：

> **“如何检索代码上下文”本身已经是独立研究问题。**

你的方向不需要重新证明“代码检索重要”，而应该进一步聚焦：

> **什么时候继续搜？搜什么？什么时候停止？在固定预算下怎么选择证据？**
